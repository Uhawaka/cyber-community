# 生成式世界引擎设计蓝图

本文是整个项目的设计蓝图：世界如何被写成包，运行时如何产生历史，文字如何从已经发生的事里长出来。质量如何判断，见[设计理念与整体质量模型](product/design-principles-and-quality.md)；目录职责见[项目结构](architecture/project-structure.md)；做到哪一步见[当前状态](status/current-status.md)。

## 要做成的事

作者给出世界资产、约束和允许的干预。Runtime 在离散 Tick 里产生客观历史。人可以旁观，也可以用 Avatar 提交一次行动尝试。叙事层只整理已经发生的事实。

世界包是大纲，不是剧本。引擎执行 workflow，不把某个世界或某个人物的名字写进运行分支。事件日志是回放的唯一来源。

本蓝图覆盖这条链：

1. 边界
2. 最小 Runtime
3. 自主相遇
4. 叙事
5. 长期状态
6. Avatar
7. 迁移
8. 门禁

蓝图不覆盖 World IDE、任意 DSL、插件生态、某一套完整长篇世界、多媒体，也不宣布文学质量已经成立。

## 权威链

```text
World Package revision
→ capability 握手与确定性编译
→ immutable CompiledWorld + typed WorkflowIR + CompiledExperienceContract
→ Runtime / Resolver
→ append-only Event Log
→ replayable Projections
→ read-only Narrative Curator / Delivery
→ independent PresentationStore
```

- `CompiledWorld` 是 Runtime 的唯一作者输入，包含规范化世界、四类 Workflow IR、分开的运行契约与编辑契约，以及内容 hash。世界种子和角色种子规定约束、倾向和长期压力，不规定事件顺序。
- Event Log 是一次运行的动态事实源。State、位置、关系、Soul overlay 和 Memory 都是可以重建的投影。
- 作者改包会形成新的 revision。已有历史只能重新开始，或从事件边界分叉。
- `PresentationStore` 保存受众游标、章节、呈现和 render version，可以写成独立文件并原子替换。它不是世界事实源。

## Workflow 的边界

世界包有四条 typed Workflow：`genesis`、`evolution`、`intervention`、`presentation`。

- genesis、evolution、intervention 使用 `world-workflow/v1alpha1`，presentation 使用 `world-workflow/v1alpha3`。
- 只能使用编译器白名单里的固定操作。
- 每条链的 steps 必须与该类的注册顺序一致。
- policy 只接受已知字段和类型。
- 由 `engine/runtime/workflow.py` 里封闭的 `STEP_HANDLERS` 执行。
- 未知操作、乱序、缺少 handler 或未注册的 renderer 一律拒绝。

因此这是四条可配置策略的封闭执行链，不是任意流程图，也不是自定义节点生态。

## 世界怎么往前走

```text
读取同一份投影
→ 环境推进与外部异变
→ 地点内按需第一次生成场景
→ 角色只看见自己眼前的一层
→ 角色提交这一手：想、说，或对共享事实动手
→ 只有动手才请环境裁决
→ 结果以类型化组件补丁进入事件日志
→ 场景、角色、Memory、Soul 与阶段投影随之更新
```

角色不从动作枚举里挑 MOVE、TALK、FIGHT。这一手只有三种去向：

- 想：只改自己，不请环境，也不进读者正文，除非其中有真正公开承担的决定。
- 说：话原样提交，并立刻加载被称呼的角色或 NPC。对方的回答也是正文。说话的人不能替对方回答。
- 做：只有移动、取放物品或改变大家都能看见的事实时，才调用环境裁决。

提到一件东西不等于动手。调度按角色主动提出的对象加载，不同对象的交互可以串行，但不要为了想或说话去问环境。一条调度链结束之前，不把这一段切成章节。

世界结构是 `World → Location → Scene → Entity components`。地点是稳定的地图节点。一个地点可以有多个场景：门口看得见的一层，和决定进去之后才出现的里间。场景第一次生成后进入事件历史，再来时读原来的状态，不重新随机。本地时钟、最近的公共回合、物件的唯一持有者、外部变化和人物位置都随事件演化。

方向分三层，不要混成同一张任务单：

- 志向是整段路的方向，一间屋子完成不了。不要把它拆成在原地反复核对的清单。
- 行事方式是稳定的：怎么看、怎么说、冲突里站在哪一边。
- 眼前这一手从现场推出来。有人等着就回答。这一处还没人说过，就只取和志向有关的那一层。这里的人已经把能说的说完，下一手就是离开。

场景问题是这一处的限度，不是第二个志向。每一处只证明肉眼能看见的那一层，不能代替下一处。重要线索散在不同地点，角色要自己走过去才找得到自己的答案。场景生成只写这里的环境压力，不指定人物反应，也不把下一站的事实写在门口。

离开当前地点，只能沿作者写好的通路去相邻地点。同一地点的里间是另一间场景，不是下一站。还没人回答这一层就声称离开，人留在原地。

环境裁决给每个已提交的回合一个戏剧进度：`none`、`advance`、`decision`、`resolved`。重复查验是 `none`，新事实是 `advance`，改变承诺、关系、持有或去向是 `decision`。只有行动已经满足这一处的收束信号，并且结果看得见，才可以 `resolved`。收束是这一处的内部节拍，不是章节刀口。

Simulation Director 还可以写入非角色事件：从作者定义的 incident 规则里选择到期、预算内、效果合法的候选，记下 `INCIDENT_OCCURRED` 或 `INCIDENT_RESTED`。incident 只有结构化的代价和效果，不预写台词、反应或结局。写了地点的规则，要等有人在那个地点才发生。UserGate 和 Fate 走单独的 intervention 路径。UserGate 的选择可以立刻记下一条看得见的观察，不能预写人物之后的反应、心理、台词或结局。

详细 Tick、追赶和冷区的粗结算都有明确预算。冷区摘要只提交可以重放的 Delta，不补写对话、秘密、关系或 Soul。

`experience_profile` 选择已经注册的通用运行方式。Runtime 只读取编译后的压力间隔、上限、决定阈值和收束模式。题材、文风、世界编号和角色编号都不能变成运行分支。

## 章节与文字

叙事策展只做选择，不是第二个世界导演。它滤掉内部调度，从已经提交、受众看得见的材料里判断一章在哪里结束。章节按内容划分，不按集数、事件条数或时间跨度配额切开。

一章应当装下一次完整的经历：进入一处、说完这一处的话、作出决定或离开。同一地点的里间不算换地方。只有赶路、还没有读者能跟上的经历，不单独成章。同一条调度链不能被切成两章。

文学层加工已经发生的对话和结果，不根据摘要另写一篇。双人以上、各有原话的章节直接装配提交过的话。只有一个人说话、或只有行动的材料，仍走四段文学管线。事实和行文门禁都要过。

- 策展、交付和渲染都不能推进 Tick、调用裁决或追加世界事件。
- 每次呈现保留来源事件、受众、章节和 render version。
- 重渲染、清空、重建或保存失败，都不改变事件日志和投影。
- Avatar 只消费自己看得见的事件。全知呈现必须显式选择 omniscient。
- 世界包通过 `experience_profile` 选择编辑 bundle、文风、固定阶段上的 Skill、Voice 和角色声音，不能注入自由提示词或代码。
- 第一次进入场景，可以用场景建立材料先给一个空间印象。再访只写已经提交的变化。
- `TURN_RESOLVED` 的公开行动、原话、反馈和组件补丁是可以引用的行动事实。文学层不用中文动作词表去猜哪些动作被允许。

默认管线依次是 `developmental-editor-v1`、`scene-writer-v1`、`line-editor-v1`、`fact-continuity-editor-v1`。世界可以在同一个固定阶段槽位里换用兼容的 Skill。每个阶段从自己的 `SKILL.md` 加载方法，留下类型化的中间结果和诊断，而不是把几份清单拼成一次总提示。文风的说法、词表和质量门禁来自资源目录。角色声音留在世界包里。二者只进入场景写作和行文编辑，不参与事实裁决。

实体、地点、线索、物件状态、台词归属、意图、心理和因果必须来自事件日志。叙事层只可以补上不改变状态、也不会变成线索的瞬时动作和节奏。默认的结构化渲染是确定性的安全回退。模型能跑通、门禁能通过，都不等于文字已经成立。

文学上的修改可以复制一份冻结的呈现，单独重渲染。这条路不加载世界执行器，不推进 Tick，并留下各编辑阶段的稿。世界素材和文学编辑要分开验收。

## 角色、长期状态与 Avatar

- NPC 保持轻量，只按本地见闻做固定范围内的回应，不替别人编历史。
- NPC 与 Avatar 共用机会、行动尝试、位置、知识、资源和代价检查，以及同一个裁决器。
- Avatar 通过严格的数据型 `AvatarPackage` 和授权入口加入。人的输入是尝试，不是结果声明。
- Avatar 不在场时策略是 `pause`：环境时间可以走，调度器不替 Avatar 行动。
- 加入、离开、再加入、Fate 和 UserGate 都写入类型化事件日志，可以回放、分叉和解释。
- Memory 的巩固要引用看得见的来源序号，并保留层级、信念类型和置信度。预算用尽或遗忘，都不删除日志。
- Soul 的作者定义不可变。批准的类型化 Delta 只更新有版本的 overlay。

## 模型与适配器

`engine/bootstrap` 是具体适配器的唯一组合处。默认使用确定性的场景生成、意图、裁决和渲染，不调用模型。只有显式传入模型配置或 `TextModel`，才装配模型场景、角色意图、世界裁决和文学渲染。

角色提示按三层填写：志向、行事方式、眼前这一手。系统可以生成提示词，但这三层的分工是设计的一部分，不能把场景问题、全部人设和世界大事堆成同一张任务单。模型不能绕过实体范围、场景边界、物件的唯一持有、完整角色的独立回应，以及来源和事实校验。

模型能接通，只说明这条链可以跑。文字是否成立，要用长程模拟和阅读来判断。

## 用世界包验证蓝图

`echo-quay` 禁止预排冲突、人物弧、台词、走位和结局，用来看变化是不是来自状态、拓扑、资源和规则。`black-pine-ridge` 用来看多地点、多角色、私有种子记忆，以及同一套引擎换一个世界还能不能跑。两个包都不能变成引擎里的特例。

两个包各自用固定 seed 做回放、不变量和历史分支检查。只改资源量或通路耗时，事件链应该跟着变。持久化恢复、冷热模拟、Fate、Avatar、呈现和规模测试的记录见[最终报告](experiments/m0-m7-final-report.md)。

这些记录证明契约还在。它们不证明世界已经好看，也不证明文字已经成立。行为是否可信、因果是否连得上、一章是否读得下去，要分开做长程模拟和阅读评审。

## 蓝图之外

- World IDE、可视化差异和创作者工作台。
- 任意 Workflow DSL、自定义节点和公共 capability 生态。
- 把某一个长篇世界写成唯一内容，或把运营流程写进引擎。
- 插画、配音、视频等多媒体。
- 用本蓝图代替对文字质量的单独判断。
