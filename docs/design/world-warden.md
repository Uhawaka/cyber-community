# 世界管家（World Warden）设计稿

状态：**草案，未实现**。目的：在写第一行代码之前，把"运行期由 agent 运转世界"这件事的边界、
接口、校验和失败模式定死，避免开工后反复返工。

---

## 0. 结论先行

**可行，但只在一种写法下可行**：管家只能新增**存在**（地点、物件、被隐藏的事实），
不能新增**发生**（谁去、谁生气、谁让步）。前者是世界的物性，后者是角色与规则的结果。

一旦它能决定"发生"，这个系统就退回被退役的导演层，设计文档 2.6「两个导演严格分权」
和 2.1「世界优先、剧情后生」同时作废。

**技术上的最大未知不在 agent，而在事实层**：`run.compiled.world` 是编译产物、不可变。
运行期新增地点需要一层可写的世界覆盖层，并且要让感知、观察、校验都从"编译世界 + 覆盖层"
读。这一点必须先做探针验证（见 §9 阶段 0）。

## 1. 为什么要做（证据，不是猜测）

| 观察 | 数字 | 说明 |
| --- | --- | --- |
| 世界材料密度直接影响产出 | 秘密 6 → 18 | 转告从 0 次变 1 次；开口从挤在头两 Tick 变成分散到 T1/T4/T4/T14 |
| 材料再多也读不到 | 18 条种子记忆，上下文里 0 条 | 召回名额被近期事件占满（已修） |
| 字段写了没人读 | `danger`、`scene_seeds` | 前者已接（`danger_here`），后者仍未接 |
| 预算本身是产出变量 | 请求上限 80 → 240 | 同种子对白 66 → 111 |

结论：**丰富度不是"写得更多"，是"到了该用的时候拿得到"**。运行期管家的价值是**及时**，
不是**更多**。

## 2. 职责边界

| 能做 | 不能做 |
| --- | --- |
| 新增一处未写过但**被暗示过**的地点 | 命令某个角色去哪里 |
| 给已有物件挂一条约束（归属、期限、缺损） | 直接发放资源、凭空出现物资 |
| 在条件成立时放出作者预留的隐藏事实 | 决定角色的情绪、动机、立场 |
| 记录"世界变了"这一事实 | 写正文、写对白、改写已提交事实 |

边界的一句话版本：**管家改的是"有什么"，不是"谁要什么"。**

---

## 3. 三个动作与事实模型

只允许三个动作，每个动作产出**一个**新事件，全部走 `commit()`，全部可校验。

### 3.1 `expand` — 补上被暗示的存在

```json
{
  "kind": "expand",
  "new_entity": {"type": "location|object", "id": "...", "name": "...",
                 "description": "...", "affordances": ["observe"],
                 "implied_by": "event:N or author:field", "adjacent_to": "location-id"}
}
```

校验（复用作者侧校验器，不另写一套）：
- id 全局唯一、不与编译世界冲突
- 只能挂到**已存在且可达**的地点旁（可达性用现有 `known_routes`/通道数据算）
- 必须给出 `implied_by`：一条已提交事件的引用，或作者源里的一句话
- 新地点初始无资源、无隐藏入口（发资源要另走 complicate）

### 3.2 `complicate` — 给已有物件挂约束

```json
{"kind": "complicate", "target_id": "object-id",
 "constraint": {"type": "owner|deadline|defect|claim", "value": "...", "source": "..."},
 "changed_state": {"quantity_delta": 0}}
```

校验：目标必须存在且被至少一个角色感知过；`quantity_delta` 必须为 0（这是**约束**，不是补给）；
同一物件同一类约束不得重复挂。

### 3.3 `reveal_hidden` — 放出作者预留的隐藏事实

```json
{"kind": "reveal_hidden", "seed_key": "scene-seed-key",
 "precondition_events": ["event:N", "event:M"], "audience": ["character-id"]}
```

这一条就是 `scene_seeds` 的用途：作者写"这里藏着一件事、什么条件下会被发现"，
管家在条件成立时让它成为事实。**它不发明内容**，只是把作者写好的东西放到该放的位置。

## 4. 触发与预算

每 Tick 都跑一个世界 agent 是把成本翻倍，且大部分时候无事可做。触发条件只允许三种：

1. **停滞**：连续 N 个 Tick（建议 N=6）没有新幕，且没有新的线索
2. **动作耗尽**：某角色的可用动作集合为空（眼前没有可交互的东西）
3. **前提成立**：某条 `scene_seed` 的 `precondition_events` 在最近窗口内全部出现

预算：
- 每个 Tick 最多触发 **1** 次，每次输出最多 **1** 个动作
- 管家调用计入 `community_max_requests`，与角色决策同池；管家花掉的请求要有单独计数
  （`usage.warden_requests`），避免"角色没说话"看起来像模型变笨

---

## 5. 可复现

这个系统的长任务价值建立在"同样的输入得到同样的产出"上。因此：

- 管家的模型输出**原样写进事件 data**（prompt 摘要 + 原始 JSON + 解析结果）
- 重放时**不重跑模型**，直接读事件 data 重建世界覆盖层
- 触发器判断必须是纯函数（只读已提交事件与预算），不能读墙钟、随机数
- 任何一步校验失败都记 `ACTION_REJECTED`（与角色决策同一处理方式），不许静默跳过

---

## 6. 与现有各层的关系

```
作者源 ──编译──> 编译世界（不可变）
                    │
                    ├── 世界覆盖层（运行期增量，只由管家事件产生）
                    │        ↑
角色决策 ──> commit ──> 事件日志 ──> 事实投影 ──> 叙事层（只写已提交事实）
                    ↑
                 管家（只在触发条件满足时看一眼，产出一个被校验的动作）
```

- **作者**：写可能性边界（什么可以存在），写 `scene_seeds` 的隐藏事实与前提
- **管家**：在边界内补存在，不改"发生"
- **角色**：照旧按上下文决策
- **叙事**：只写事实层；管家新增的实体必须带"可感知描述 + 可交互动作"，否则正文引用不到

## 7. 失败模式与对策（每条都要有测试）

| 症状 | 机制原因 | 对策 | 测试 |
| --- | --- | --- | --- |
| 管家变成导演 | 动作里含"谁去做什么" | 事件 schema 里根本没有 actor 字段 | 构造含 actor 的提案必须被拒 |
| 世界无限膨胀、密度稀释 | 无节流 | 每次 ≤1 动作、每 Tick ≤1 次、新增实体 30 Tick 内不得再扩 | 连跑 30 Tick，实体增量 ≤ 上限 |
| 新增地点没人去 | 只加了地图 | 新实体必须带 affordances，且必须挂在一个**有人常去**的地点旁 | 新实体在 20 Tick 内被访问 ≥1 次 |
| 正文写不出新实体 | 缺少可感知描述 | schema 强制 `description` 非空 + 至少 1 个 `affordances` | 观察命令能引用新实体名 |
| 与已提交事实冲突 | 没有一致性校验 | 复用 `package_validation` 的规则集 | 构造冲突提案必须被拒 |
| 重放不一致 | 读墙钟/随机/重跑模型 | 事件存原始输出，重放不调模型 | 同日志重放两次，哈希相同 |
| 成本翻倍 | 每 Tick 都跑 | 三种触发 + 同池预算 | 24 Tick 的 `warden_requests` ≤ 4 |
| 管家凭空发资源 | 动作里带 quantity_delta | 强制 0，补给要走角色动作 | 非零 delta 必须被拒 |

## 8. 被否决的方案

- **每 Tick 都跑一个"世界 agent"**：成本翻倍，且 90% 的 Tick 没有扩增的必要；改成条件触发。
- **让管家直接生成"下一条事件"**（谁做了什么）：这正是退役的导演层，且会与角色的决策冲突，
  同一 Tick 出现两个决策源。
- **让管家写正文**：叙事层的硬规则是"每个名词、数字、引语都要追到已提交事实"；
  生成正文却不生成事实，等于把不可核对的内容塞进成品。
- **只加地图**：地图不产生张力。张力来自稀缺、期限、所有权和秘密；纯扩地图是最贵、最无效的加法。

## 9. 分阶段落地与验收

### 阶段 0（已完成）：事实层探针结果

探针（种子 17 的 `_r9_17` 运行，中途把 `run.compiled.world.locations` 换成一个多了一个
地点的版本）：

1. **替换 `run.compiled` 可行**，感知照常返回（10 个可见实体），没有崩。
2. **移动提交"成功"，但地点没变**：`commit(MOVED, location_id="probe-yard")` 没有报错，
   之后 `perceive` 仍然报 `shared-court`。

第 2 条是这次探针最重要的发现：`event_validation.py:244` 会把**不在
`run.state.location_ids` 里的目标静默降级成 `None`**。也就是说运行期新增地点必须**同时**
登记到 `state.location_ids`，否则得到的是"事件提交成功、世界没变"——最坏的一种失败：
日志看起来正常，行为没发生。

由此确定的实现要求：

- **读路径要覆盖 5 处**：`community_perception.py:11`、`opportunities.py:80`、
  `community.py:304`、`community.py:345`、`community_context.py:96`（危险度）；
  一律改成"编译世界 + 覆盖层"，不许各改各的
- **写门禁要同步**：`state.location_ids` 必须随覆盖层增长（且 `state.py` 的 `__post_init__`
  会去重排序，登记顺序不能当语义）
- **通行是独立实体**：`world.passages` 只有 14 条，新地点没有 passage 就走不到。
  所以 `expand` 一次至少产出**两个**实体（地点 + 一条通路），否则等于造了一间没有门的房间
- 覆盖层**不进 `compiled`**：`compiled.content_hash` 参与世界哈希与重放，运行期改它等于换了世界。
  覆盖层必须是从事件派生的纯函数（`world_overlay(run)`），重放时由事件重建

结论：`expand` 可行，但比设想的多两件事（通路 + 门禁登记）。如果实现时只想动一处，
那就不要做 `expand`，只做 `complicate` 与 `reveal_hidden`。

### 阶段 1：接通 `scene_seeds`（不改世界，只放隐藏事实）

- 绿：20 Tick 内出现 ≥1 次 seed 触发，幕数 1 → 2，逐字复读不上升
- 黄：触发但不增加幕 → 问题在场景层，不在世界层，停止扩展世界
- 红：永远不触发 → 前提条件写得太严，或投影没做

### 阶段 2：`expand` + `complicate`

- 绿：新增实体在 20 Tick 内被正文引用 ≥1 次；世界校验零诊断；`warden_requests` ≤4/24 Tick
- 黄：实体被访问但没写成幕 → 先修场景层

## 10. 未决问题（需要拍板）

1. **管家能不能改资源数量**？我倾向不能（补给必须由角色动作产生），但"灾害毁掉一部分存粮"
   这类事件算不算世界侧？如果算，它就必须能改数量，只是方向只能是**减**。
2. **新增地点的作者授权边界**：我倾向"作者写可能性边界（哪些方向可以扩、哪些绝不可能）"，
   管家只在内侧增生。否则同一个世界跑两次会变成两个不同的世界。
3. **管家给不给角色看**：角色该不该知道"世界刚刚变了"？我倾向不主动告知，改变只能通过
   感知与亲身经历进入角色认知——否则等于给角色发剧本。
4. **停滞判定用"没有新幕"还是"没有新线索"**？前者会被场景层的能力限制误伤
   （场景层只会写三型），后者更宽松。建议先用线索，等场景层扩了再收紧。
5. **要不要顺手修掉那个静默降级**？`event_validation.py:244` 在目标不在
   `state.location_ids` 时把坐标设成 `None` 而不是拒绝。这是探针撞出来的既有行为，
   与管家无关，但管家一旦上线就会频繁踩到。我倾向改成显式拒绝（`ACTION_REJECTED`
   里带原因），代价是可能有旧日志/旧测试依赖这个宽松行为，需要先跑一遍全量确认。

## 11. 离线模拟结论（2026-10-29，`~/labs/research/cyber-community/warden_sim.py`）

拿真实运行日志跑机制模拟（不调模型），四组运行（`_grown17` / `_r9_17` / `_full_17` / `_cool17`）：

| 检查项 | 结果 | 含义 |
| --- | --- | --- |
| 停滞触发（连续 6 Tick 无转折） | 24 Tick 的局 **0 次**；13 Tick 的 `_cool17` 1 次 | 健康的局里几乎每个 Tick 都有 request/promise/clarify，**这个触发器基本不会响** |
| 静默 Tick（无动作／只等待） | **0 个**（四组皆然） | 第二个触发器同样不响 |
| 作者 `scene_seeds` | **0 条**（三套世界） | `reveal_hidden` 没有内容可放，第三个触发器无从谈起 |
| 移动事件 | **0 条**（24 Tick 内角色不换地点） | 新增地点**不会有人走到**——`expand` 现在是最弱的一环 |
| 带转折的对白 | 37–48 条／局 | 材料是够的 |
| 写出的幕 | **1 幕** | 场景层才是瓶颈 |

三条判断因此改变：

1. **现在不该建管家。** 三个触发器在真实运行里一个都不响，建出来就是空转的模块。
2. **`expand` 要往后放。** 24 Tick 内零移动，加了地图没人去；先要回答"角色为什么不移动"
   （是日程把人都钉住了，还是移动被别的东西挡住）。
3. **瓶颈在场景层。** 37–48 条带转折的对白只写出 1 幕，其中 14–26 条是只有 `clarify` 的问句，
   现有生产者一个都不认。同样的材料，场景层能写几幕，比世界里多几个地点重要得多。

因此顺序改为：**先扩场景层的容量（clarify 也是转折、一次观察允许两幕），再回来重跑这个模拟**。
如果那时"转折 → 幕"的比例上去了，世界侧的扩增才有意义；如果上不去，加世界只是把瓶颈藏得更深。

附：跑模拟时发现自己污染过一次 `_r9_17.jsonl`（探针 `commit` 写进了真实日志，多出 1 条移动到
`probe-yard` 的事件）。已删除该行、保留 `.bak`，复核事件数 483、对白 95，与原文一致。

## 12. 更正：`expand` 的前提已经成立了一部分（2026-10-29 晚）

§11 写过"24 Tick 内零移动，所以 expand 要往后放"。这条结论**已被推翻**：

- 移动本来就是 0，不是因为没路，而是因为**没有理由去**（作者的 goals 社区运行时根本不读）
- 接通 `authored_goals` + 结构化 `errands` 之后，同种子移动 0 → 7（种子 23 为 0 → 3），
  六个人全都有出门

所以"没人走"是作者侧缺口的症状，不是世界不该扩。管家 `expand` 的可行性判断改为：

- 只有当世界里有**跨地点的欠着的事**（东西在别处、有人挡着）时，新地点才有人去
- 因此 `expand` 必须和 `complicate` 配套发布：单加地图仍然是造没门的房间，
  加了"东西在别处被人占着"才有腿
- §11 里三个触发器不响的结论仍然成立（健康的局里几乎每 Tick 都有转折），
  所以管家仍然不能按"停滞"触发，只能按 `scene_seeds` 的前提或"差事走不通"触发
