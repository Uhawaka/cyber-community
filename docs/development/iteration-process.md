# Workflow 与 Runtime 协同迭代流程

本项目不能先闭门设计一套“完整 Workflow”，再一次性实现万能 Runtime。世界格式、运行机制和质量标准必须通过可运行世界反复校准。本流程用于防止两种失败：把世界内容硬编码进引擎，或为了抽象而实现没有产品证据的通用系统。

## 1. 两个循环

```text
产品发现外环
设计假设 → 世界包/Workflow revision → 模拟 → 质量评估
→ 保留、修改或删除机制 → 稳定后形成规格

运行验证内环
CompiledWorld → Runtime → Event Log → Projection
→ Narrative Delivery → 指标、追踪与失败诊断
```

外环决定“这个机制是否值得存在”，内环证明“它是否按契约执行”。一次迭代应优先只改变一个主要变量，否则无法判断结果来自 Workflow、Runtime、模型还是世界内容。

## 2. 需求分类

开始编码前，先将需求归入一类：

- **内容变化**：角色、地图、资源、世界规则、阈值；优先修改世界包。
- **策略变化**：已有通用步骤的顺序或 policy；修改 typed Workflow。
- **通用机制候选**：现有 Workflow 无法表达、多个世界都需要的结算语义；进入实验。
- **事实完整性修复**：replay、原子性、权限或安全错误；直接修内核并补回归。
- **呈现变化**：来源选择、Episode 组织或文学表达；只修改 Narrative。
- **产品界面变化**：创作、观察或参与流程；不得反向污染 Runtime 权威边界。

若一个需求同时横跨多类，应先写清每层输入和输出，再分别交付，不要用一个“Director”或“Agent”对象吞掉全部职责。

## 3. 一轮迭代的标准步骤

### 步骤 A：写单一假设

使用 `docs/experiments/README.md` 的模板，在 `outputs/experiments/` 创建实验报告，明确：

- 改什么；
- 预计哪个可观察结果变化；
- 哪些事实和边界必须保持不变；
- 什么结果意味着失败；
- 运行的世界、seed、Tick 和预算。

错误示例：“让剧情更好。”  
可验证示例：“加入移动目的冷却后，40 Tick 内非目标往返下降，同时采集、会面和关键状态变化不减少。”

### 步骤 B：先构造最小世界探针

优先在世界包和 Workflow 层表达假设。探针只保留能触发机制的角色、地点、资源和规则，并包含一个预期失败路径。

不要一开始用大型《西游后传》内容调试基础机制。复杂内容会掩盖因果，也会诱导执行器出现世界专名。

### 步骤 C：生成编译差异

记录 package revision、content hash、Workflow hash 和规范化 IR。编译器必须在运行前拒绝未知字段、非法引用和不支持 capability。

如果改变作者文件却没有改变编译结果或运行可见输入，应先修编译链，而不是继续调 Runtime。

### 步骤 D：建立基线

至少保存：

- 固定 seed 的事件类型和 history hash；
- 最终位置、资源、关系和关键投影；
- 拒绝、重规划、预算耗尽和 Gate；
- Episode 数量、来源范围、长度和内部事件泄漏；
- 当前人工评审结论。

实验报告、指标和原始结果统一保存到 `outputs/`；测试报告保存到 `outputs/tests/`。
正式回归所需的冻结输入单独提炼到 `tests/fixtures/`，不依赖本地输出是否存在。
`docs/` 只记录规范、开发检查点和产出索引，不保存实验或测试产物。

### 步骤 E：做最小实现

按“世界包 → Workflow policy → Runtime capability”的顺序寻找最小变更。Runtime 新能力必须：

- 使用 typed 输入、输出和错误；
- 不含世界专名；
- 通过 Event Log 提交事实变化；
- 明确预算、停止和失败行为；
- 支持 replay；
- 不给模型额外事实权限。

### 步骤 F：四层验证

1. **单元与契约**：正常、非法和原子失败路径。
2. **架构**：依赖方向、公共入口和 adapter 隔离。
3. **多 seed 模拟**：至少两个世界包，观察分布而非挑最好样本。
4. **叙事评审**：事实追溯、可读性、信息增量和追更动力。

模拟通过但正文差，通常应先改 Curator 或 Renderer；正文好看但无法追溯事实，必须判失败。

### 步骤 G：决定机制去向

- **保留在世界包**：只对某题材或某世界有意义。
- **保留在实验层**：证据不足，继续迭代。
- **晋升 Workflow policy**：语义稳定、只需配置差异。
- **晋升 Runtime capability**：至少三轮独立实验、两个世界、稳定失败语义且无法合理留在内容层。
- **删除**：增加复杂度但没有稳定改善，或只能靠硬编码成立。

安全、数据完整性和 replay 修复不受“三轮”限制，但必须补回归。

## 4. 质量回归包

每次影响行为或叙事的变更，至少执行以下组合：

- `echo-quay`：反剧本、小规模、Gate 与短因果链；
- `black-pine-ridge`：多地点、三角色、私有记忆与长期行为；
- 8 个固定 seed 的短程 probe；
- seed 17 的 40 Tick 可读输出；
- 一个资源或通路单变量扰动；
- 一条非法输入或权限失败路径。

涉及长期机制时再增加 100 Tick soak；涉及冷区时增加 detailed + catch-up；涉及 Avatar 时增加 join/leave/rejoin 和历史分叉；涉及模型时保留无模型基线并验证越界回退。

## 5. 指标解释

指标用于发现退化，不能代替产品判断：

- 移动次数高，可能是探索，也可能是随机游走；需检查目的和状态收益。
- 事件数量高，不代表世界丰富；可能只是内部抖动。
- history hash 多样，证明有分叉，不证明分叉有意义。
- 对话次数高，不代表关系发展；需检查信息增量和主题重复。
- Soul 变化多，不代表角色成长；可能是人格漂移。
- Episode 覆盖事件多，不代表叙事完整；可能是流水账。

因此每个数值异常都应回到事件来源、前后状态和人工阅读进行解释。

## 6. 变更提交要求

一项机制完成时，相关改动应同时包含：

- 世界包或规格变化；
- 编译/执行实现；
- 至少一个失败测试；
- 可重放模拟证据；
- 必要的 ADR 或边界更新；
- 当前状态文档中的完成度与已知限制。

不要先更新路线图为“完成”再补证据。完成口径必须说明它是技术能力、内容质量还是用户验证。

## 7. 当前推荐迭代顺序

按需调度、内容分章、分层线索和三层角色提示已经接上。下一轮不要把它们重做成事件配额或动作枚举。当前顺序：

1. 用第二个世界确认：门口不写出后一站的事实，这一层说过之后人会沿通路离开。
2. 非对白章节仍走文学管线。回退正文不能露出实体编号，也不能把同一句说两遍。
3. 对话只取这一处的一层，不把场景问题写成第二个志向。
4. 收紧 Soul 演化证据与频率。
5. `actor_windows` 世界仍要保持合法竞争，不要为了场景路径删掉 reservation。
6. 建立 100 Tick 多 seed 质量基线，再单独判断文字。

这一路径先修正“世界为什么这样行动”，再优化“怎样把它讲好”，最后才扩大内容和模型投入。
